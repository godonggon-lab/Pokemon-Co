# Phase 14. 채점 제한값과 스트레스 기반 강화

## 목표

문제 수가 늘어난 상태에서 TLE, MLE, OLE 같은 실행 verdict가 실제 채점 경로에서 안정적으로 동작하도록 제한값 관리 계층을 분리한다.

## 이번 단계에서 고정한 것

- `harness/limits.py`에서 문제별 제한값을 중앙 계산한다.
- BOJ 스냅샷의 시간 제한을 사용하되 Docker 실행에서는 최소 1초를 보장한다.
- 현재 스냅샷의 메모리 제한값은 `1`, `2`처럼 잘못 파싱된 항목이 많으므로 Docker 컴파일 오탐을 피하기 위해 최소 256MB로 보정한다.
- 출력 초과는 기본 64MB 제한을 사용한다.
- `/judge`, `/run` 서버 경로가 정규화된 제한값을 DockerRunner에 넘긴다.
- Next API와 문제 화면도 같은 기준으로 제한값을 보정한다.

## 검증 명령

```bash
npm run judge:limits
npm run harness:test
npm run judge:docker-check
```

## 현재 의미

- 무한 루프 코드는 `TLE`로 잡을 수 있다.
- 과도한 메모리 사용 코드는 `MLE` 또는 언어 런타임의 메모리 에러로 잡을 수 있다.
- 과도한 출력 코드는 `OLE`로 잡을 수 있다.
- 단, 문제별로 TLE를 유도하는 최대 입력은 아직 모든 문제에 들어간 상태가 아니다. 다음 단계에서는 고위험 유형부터 스트레스 케이스를 보강한다.

## 다음 단계

2. 각 유형별로 최대 입력 또는 최악 패턴 입력을 override에 추가한다.
3. 정상 정답 코드가 통과하고, 느린 코드가 TLE로 잡히는 대표 회귀 테스트를 만든다.
4. nightly workflow에는 비싼 스트레스 검증을, quick-checks에는 빠른 메타 감사만 둔다.
